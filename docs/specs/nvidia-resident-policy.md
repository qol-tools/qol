# Resident NVIDIA Policy

Living architecture contract for durable NVIDIA driver policy in qol-tools. This document is timeless: it carries contracts, not snapshots. Implementation waves land against this text; the text does not chase implementations.

## Mission mapping

The host ownership contract comes from the qol-mission skill. Portable permits only session-scoped mutations that restore exactly. Resident is explicit opt-in for a trusted host and permits durable policy with snapshot-before-mutation, exclusive ownership of introduced state, visibility, and exact restoration on disable or uninstall.

NVIDIA driver observation is Portable-safe and always on. Durable NVIDIA policy is Resident-only.

## Observation contract

The gpu_driver_sync feature owns one typed observation consumed by doctor and watch alike. There is exactly one crate-visible observe function and no exported raw probe values.

The observation distinguishes:

- Unsupported: the platform cannot observe.
- NotLoaded: no NVIDIA kernel module is loaded. A missing Linux proc file means NotLoaded.
- LoadedUnavailable: the loaded probe failed for a reason other than a missing file.
- OnDiskUnavailable with the known loaded version: the on-disk module version is unknown.
- Matched with the loaded version.
- Mismatch with the loaded and on-disk versions.

## Watch contract

The watch is read-only and never blocks a Tokio worker: observation runs through spawn_blocking. A typed latch transitions on each observation:

- Unsupported and either Unavailable state preserve an existing latch.
- Positively NotLoaded or Matched clears the latch.
- A new Mismatch pair sends once, the same pair dedupes, a changed pair sends again, and a mismatch after a positive clear sends again. A mismatch followed by an unavailable state followed by the same mismatch must not resend.

Notifications go through the shared surfaces notification path with a protocol level, never through a second notification command.

The watch lifecycle stops by direct quiescence of the in-flight probe generation: stop signals the running generation, awaits its quiescence, and then waits for the published Idle state, all within one bounded backstop. The watch task exits when its shutdown sender is dropped; it never polls for shutdown. If a probe outlives the backstop, stop returns while the lifecycle stays Stopping for that generation until the supervisor retires it, and a replacement watcher is never spawned over a live generation, so probe runs never overlap.

## Trace contract

The feature emits stable GPU_DRIVER_SYNC_OBSERVE and GPU_DRIVER_SYNC_NOTIFY events with key=value outcomes: unsupported, not_loaded, unavailable, matched, mismatch for observe; sent, deduped, preserved, cleared for notify. Notify may carry a policy=<intent> key (none, preparing, active, drifted, missing-fragment, releasing, release-failed, unavailable). The trace runner maps the GPU_DRIVER_SYNC_ tag prefix to the gpu-driver-sync source, formats the events, and retains them under the source filter.

## Policy intent contract

The feature also owns one typed, read-only policy-intent view consumed by doctor and watch alongside the observation. Intent and live state are distinct inputs and are never conflated:

- None: no journal, an unjournaled fragment, or an unknown policy. The view never claims operator state.
- Unavailable: the status query failed, or the journal is Active or Drifted without a proven expected module version.
- Preparing: adoption is in flight or was interrupted.
- Active with the expected module version proven at adoption.
- Drifted with the expected module version proven at adoption.
- MissingFragment: the journal is active but the owned fragment is absent.
- Releasing and ReleaseFailed are explicit intents and are never referenced by policy wording.

The view is queried by reading the journal and the fragment only; it never mutates, never escalates, and is safe for the unprivileged tray process because journal and fragment are world-readable by construction. Policy wording is allowed only for a proven Active or Drifted view; every other intent keeps generic live wording. Intent comparisons use only the expected module version, never package versions: the tray never compares a 580.x-0ubuntu package version to a 580.x module version.

## Doctor contract

Doctor is a CheckReport formatter over the observation and the policy-intent view. It owns no comparison, no probe, no mutation, no advice. Every observation shapes a report with empty advice and empty fixes. Resident policy must never become a FixApplicability tier: mutation lifetime and doctor authority are orthogonal concepts.

## Durable policy state machine

The authoritative journal is machine-scoped, root-owned, durable, readable for status, and keyed by policy with a set of ResidencyOwnerId owners. Owners are a stable host-local lineage derived from the machine identity, not from an InstallId, so ordinary installer updates never rotate or lose ownership. First owner adopts, additional owners join without mutation, releasing any owner removes that owner, and physical restore happens only when the set becomes empty. Transfer is an explicit atomic owner-set replacement. The active fragment identity is proven against the journal before any owner expansion or owner no-op. Disable and uninstall are fail-closed.

Every journal and resource mutation runs under a residue-free cross-process lock: an abstract Unix-domain socket in the kernel namespace, bound per policy, released automatically when the holder dies, retried with a bounded window, and never leaving a file behind. Busy means contention only: socket creation failures and non-EADDRINUSE bind failures return immediately as a distinct LockFailure. Test and sandbox builds inherit a valid explicitly set lock namespace and are isolated only under it; without one they deliberately use the stable production base name and therefore may contend on the same lock. The typed ResidentPolicy registry is required for every mutating API; unknown policy ids are rejected before any status or mutation, and observation stays a read-only Portable function. Non-Linux platforms expose the same API surface with a typed PlatformUnsupported error.

One shared typed strict argument parser serves qol-tray, the qol-resident-policy adapter, and the hidden __resident-policy-* commands: missing values, duplicate or unexpected flags, trailing arguments, unknown policies, invalid owners, and op-inappropriate flags (an owner for status/help/enable, a policy for help) are rejected before any root or pkexec boundary, and join and transfer require an explicit owner. The parser accepts no caller-supplied root or elevation bypass: privilege comes only from the process's own elevation, never from a flag. Escalation rebuilds the privileged argv only from the parsed command, never by re-reading process arguments. The command shape is identical on every platform, and unsupported platforms parse that same shape first and fail typed before elevation.

States:

- Absent: no journal, no host mutation.
- Preparing: adoption has begun, snapshot and journal write are in flight.
- Active: policy applied and verified.
- Drifted: reconciliation observed operator drift.
- Releasing: disable or uninstall in progress, releasing only verified live qol-owned resources.
- ReleaseFailed: release could not complete; expected-versus-actual hash evidence is preserved in the journal and surfaced by status.

Transitions:

- Absent to Preparing on adoption.
- Preparing to Active once verified.
- Active to Drifted on observed drift.
- Active or Drifted to Releasing on disable or uninstall.
- Releasing to Absent after the final successful release; the exact canonical journal and its fixed recovery stage are removed.
- Releasing to ReleaseFailed on failure, preserving evidence.
- An owner set with members remaining after a release stays Active; the fragment is untouched until the last owner releases.

Recovery rules:

- Only Preparing may complete an interrupted adoption. Adoption renders the exact final bytes (mode 0644, fsynced) into an unnamed private resource inside the fragment directory, links it to a journaled staged name, and publishes atomically with renameat2(RENAME_NOREPLACE); the final path is never written directly. A crash during the unnamed write leaves no named residue; a crash after the link leaves exactly one staged file whose content is provably ours (hash equals the journaled plan); recovery publishes a provably-owned staged file and preserves any staged-path collision byte for byte while rolling the journal back to Absent and aborting the adoption. An interrupted Preparing resumes only against the exact planned resource: the fragment must be absent or byte-identical to the planned rendered hash, and any other file at the owned path is preserved and the journal is rolled back to Absent without adoption. Adoption also refuses an ambiguous module ownership: if the module path resolves but no module owner package is recorded, the host is left unchanged. A Releasing journal resumes the release; a ReleaseFailed journal retries the release and re-records evidence on each failure. An unprovable staged fragment collision stays a visible ReleaseFailed with the collision and the journal preserved; it never rolls silently to Absent. A dangling fragment symlink is unjournaled drift (never Absent), and every journal, fragment, and staged file is opened with no-follow open plus same-descriptor fstat so replacement races cannot be hashed as regular files.
- Active reconciliation observes drift and never recreates or re-expands removed state.
- Partial removal becomes visible drift; release targets only still-live state that the journal owns.
- Releasing retries only verified live qol-owned resources.
- There is no persisted Released state: Absent is reached by removal, not by a tombstone.
- Join and release are idempotent: joining an existing owner and releasing an absent owner are no-ops. Join and transfer are defined only for an Active policy; Releasing and ReleaseFailed carry exactly one terminal owner; disable unwinds Preparing deterministically when the resource is absent or exactly known and records ReleaseFailed evidence otherwise; every release failure, including remove and fsync failures, persists typed stage evidence (fragment-verify, fragment-remove, fragment-publish, staged-cleanup, journal-remove) while keeping the payload for a retry. Invalid states are unrepresentable: schema 9 journals deny unknown JSON fields, the embedded policy must match the tagged payload, the resource identity is a policy-bound true nonce (never timestamp+pid), the expected module version is mandatory and snapshotted from the module probe (resolution failure leaves the host unchanged), the rendered hash is recomputed from the exact rendering on every read, owners are constructed only through validated parsing, timestamps are nonzero, and release-failure hashes are typed and internally consistent with the payload.
- The journal is schema-versioned (schema 9) and carries a serde-tagged policy payload: the generic journal owns policy id, owners, lifecycle state, failure evidence, and its own embedded JournalFileIdentity; the NVIDIA payload owns the exact package entries, the expected module version, a unique resource identity, and the rendered-fragment sha256. Journal invariants are validated on every read: schema version, embedded policy matching the requested file, non-empty validated owner set without duplicates, payload presence in every state including ReleaseFailed, failure evidence only in ReleaseFailed (with valid hashes, stage, and path), validated package entries without duplicates, usable identity and module-version fields, and a sha256-shaped rendered hash. read_journal rejects a valid journal whose embedded policy differs from the requested one. A retry clears stale failure evidence before proceeding.
- The journal is one exact top-level file under the pre-existing /var/lib: the canonical path /var/lib/qol-resident-policy-nvidia-driver-version-pin.json and one exact fixed recovery stage /var/lib/.qol-resident-policy-nvidia-driver-version-pin.json.stage. The test/sandbox directory override selects an already-existing parent but keeps those exact basenames; the parent is never created, chmodded, scanned, or removed, and unrelated /var/lib entries are preserved byte for byte. Writing opens the parent pinned no-follow, creates an unnamed O_TMPFILE, applies exact 0644 with root:root ownership in production (current euid/egid only in test/sandbox), fstats its identity, serializes the journal with that identity embedded, writes and fsyncs, links no-replace to the fixed stage (AT_EMPTY_PATH when privileged, otherwise the owned descriptor through /proc/self/fd with AT_SYMLINK_FOLLOW), validates the linked stage identity immediately, and strictly fsyncs the parent. The first canonical commit uses renameat2(RENAME_NOREPLACE); an update first validates the existing canonical through one descriptor, carries its dev/ino, revalidates the name immediately before replacement, and refuses to clobber if the identity changed, then renames and strictly fsyncs the parent. Normal failures clean only the exact stage created by that invocation after identity proof and report combined cleanup failures. A named fixed stage is recoverable only when it is a regular schema-9 journal for the exact policy whose embedded identity matches that exact inode; under the policy lock, enable, disable, join, and transfer recover such an interrupted stage by removing it and strictly syncing before any read, rolling an interrupted write back to the old canonical or Absent. Invalid, nonregular, symlinked, or byte-copied wrong-inode stage collisions are preserved and fail closed. Read-only status and read_journal never mutate and return a visible interrupted-or-invalid error whenever the stage exists, never Absent. Final removal validates and immediately revalidates the canonical identity, unlinks only that exact file, and strictly fsyncs /var/lib. Directory fsyncs are the policy-local strict variant that propagates EINVAL and EROFS, used for fragment publication and removal syncs too. The fragment create is no-clobber (O_EXCL), fsynced, mode 0644, and the parent directory is synced. The resource identity is rendered into the fragment as a header line and the planned hash is computed from that exact rendering before any mutation; finalize_active never rewrites the planned hash from whatever file landed, and resume, status, and release all verify the planned hash against the live bytes.

## Wave 2 ownership premise

apt-mark hold is rejected as the resident ownership primitive because its global dpkg selection bit carries no owner identity and cannot be attributed to a qol InstallId.

The candidate primitive is a fixed, uniquely qol-owned APT preferences fragment containing exact adopted package versions, backed by the root-owned machine journal with its ResidencyOwnerId owner set and expected resource identity.

Adoption must refuse a pre-existing unjournaled path and create without clobber. Release removes only a resource whose identity still matches the journal; disagreement becomes visible Drifted or ReleaseFailed. Adoption also gates on a dpkg-based host: a non-APT host is refused with a clear error before any journal write. Debug-seam target patterns are validated before use.

The target set covers the fixed installed module-bearing and coherency families for both DKMS and precompiled installs: nvidia-driver, nvidia-driver-*, nvidia-kernel-*, nvidia-dkms-*, nvidia-headless-*, and linux-modules-nvidia-* (Ubuntu precompiled modules). When the nvidia module path resolves via modinfo, that exact path and every dpkg co-owner of it are resolved exactly once through argv-safe dpkg-query. All co-owners must be strict approved module families and activation-installed with exact versions included in the pin set; a foreign, unapproved, or unproven co-owner fails adoption before any journal mutation. nvidia-utils and lib packages stay excluded. The expected module version is snapshotted from modinfo -F version nvidia at adoption and never inferred from a Debian package version; it is exposed through the typed status view and is the only value the tray intent compares.

A disposable Debian or Ubuntu guest must prove upgrade, full-upgrade, unattended-upgrade, collision, drift, crash, owner-set release order, idempotence, update continuity, and final residue behavior through the real production operations before Wave 2 implementation is authorized. If the preference mechanism fails that gate, stop for architecture. Never silently fall back to apt-mark.

## Standing corrections

- Extend qol-host-fixes for privileged work. Do not create a parallel crate.
- The privileged adapter lives in the shipped qol-tray artifact, not the developer-only qol CLI.
- The qol-resident-policy companion binary is a deliberately shipped, first-class deployable artifact of the qol-tray package with its own typed BuildRole (ResidentPolicy), binary name constant, embedded build identity, and a place in the exhaustive deployable identity tests. It is installed at /usr/lib/qol-tray/qol-resident-policy in the Debian package, accepts only the fixed operations (status, help, enable, disable, join, transfer) plus the hidden __resident-policy-<op> command shape through the shared strict parser, and is the prerm release vehicle. The Debian package is the only Resident carrier: user-local installs, raw release tars, and source runs are Portable forever and cannot enable resident state (the managed gate refuses them with a typed error, and there is no user-local marker, adapter, or uninstall expansion). A system-wide Debian install never self-updates from the Portable host-only tar: the tray update path refuses the tarball for SystemWide installs with package-manager guidance (apt-get update && apt-get install --only-upgrade qol-tray, or reinstalling the new .deb). The resident-wave2 workflow builds the artifacts itself and stages only identity-verified references (sandbox-intent adapter, development-intent plain adapter, and the real production-intent cargo-deb package whose extracted payload is verified for both binaries before staging) with no filename or target-directory rediscovery. The resident gate bundle product key binds the recipe revision, the source closure, the tool invocation and canonical paths with their exact versions, the fixed build recipe (per-step profile and features), and the sanitized inherited build inputs; every probe and build runs from the supplied worktree, and scenario-only text stays outside the closure and the key. A child process resolves the bundle and publishes a fully validated run-owned snapshot while holding the cache lock; the parent never recomputes a key and never consumes the shared cache after the child exits. Immutable payload flow admission requires a declared image_revision only for Desktop workflows, never for ResidentWave2, and workspace mounts remain forbidden for every immutable payload. Guest-only fixture behavior lives behind a distinct non-shipping sandbox feature and sandbox build intent that are never in release artifacts.
- Privileged entry points are operation-specific and argv-safe: no write-json, no arbitrary path, no arbitrary package list, no shell-string API. One shared strict parser rejects unknown, duplicate, missing, and trailing arguments for the tray hidden route, the adapter, and the installer before any root check, then validates the policy id and the fixed operation set before dispatch and recomputes the fixed NVIDIA target set inside the privileged process; the privileged argv is built only from the parsed command. Unknown operations, malformed arguments, and unsupported platforms fail before pkexec; successful privileged stdout and stderr are forwarded to the caller. Disable and uninstall are fail-closed: a release failure persists typed ReleaseFailure evidence bound to the release stage (fragment-verify, fragment-remove, fragment-publish, staged-cleanup, journal-remove), the payload is kept for retry, and evidence-write failures are never ignored.
- Linux coordination uses a residue-free process lock abstraction, preferably an abstract Unix-domain socket, never a permanent lock file that cannot be race-safely removed.
- The journal carries the policy-specific tagged payload inline: target resources, pre-existing state, and only qol-introduced state. There is no external snapshot PathBuf.
- Reconciliation never expands owned state after operator drift.
- Direct apt upgrade is excluded from the mutation milestone. Enable, release, status, reconciliation, and uninstall restoration land first.
- The Debian package ships prerm and postrm maintainer scripts: prerm releases the stable host owner through the installed adapter on remove and purge before the binary disappears, never during upgrade, and aborts the removal (fail-closed) while preserving evidence if the release fails; if the adapter is missing but active resident state exists, prerm aborts the removal rather than silently leaving policy behind, using POSIX no-follow detection ([ -e ] || [ -L ]) so a dangling or special resource also fails closed. postrm never touches /var/lib or /home; the adapter's durable release owns removal of only the exact canonical journal and its fixed stage, and prerm fails closed on either exact path before and after the adapter release. The guest gate exercises the real dpkg package lifecycle, including upgrade continuity and final residue after uninstall.
- Resident activation (enable) succeeds only under a system-wide Debian install: the adapter runs at the fixed deb path and refuses raw, portable, development, and sandbox artifacts with a typed error, never creating unrecoverable resident state. Carrier proof is graded and enforced at every public mutation boundary under the policy lock before any recovery: activation-grade enable, join, and transfer require the qol-tray package with dpkg desired install or hold and currently installed, while release-grade disable and prerm also accept desired remove or purge while the package is still currently installed. The plain installer is unchanged (a plain install-id text file; no marker, no bundled adapter, no uninstall expansion, no user-local Resident surface), so non-Linux and user-local installer behavior does not regress.
- Global qol-tray help lists resident-policy; resident-policy help explains the durable host-local effect and the enable/status/disable/join/transfer syntax without elevation.
- Synced profile data must never activate a residency policy: activation is host-local and explicit, and the operations accept no profile-derived input.
- Controllers modprobe persistence is separate architectural debt and a future consumer of the same vocabulary; it does not broaden the NVIDIA wave.

## Acceptance plan

Unit tests cover the journal state machine transitions, interrupted adoption at every crash boundary (after-journal, after-unnamed-staged-write, after-link, after-publish), pre-held resource preservation, drift evidence, staged-path collision preservation byte for byte, the watch latch transitions, the intent mapping, intent-aware doctor wording, the cross-process lock (exclusive between threads and across clean subprocess execs, residue-free), the concurrent enable/enable and enable/disable races, the operator-file-at-resume rollback, negative journal-validation cases, module-version snapshots with realistic Debian package versions, the watch initial-only and shutdown behaviors, the shared strict parser, the deployable identity registry-to-manifest bijection, and the deb-lineage-gated managed install (fixed deb adapter path, no user-local or sandbox bypass). Lock and crash probes use clean subprocess helpers, never fork-from-multithreaded tests. The guest gate always creates its stage with mktemp inside the guest on disk-backed /var/tmp (surviving the mid-scenario reboot), rejects symlinks, validates the exact owned target before cleanup, and never accepts a STAGE override. The watcher event channel is bounded and coalescing; the watch task exits when its shutdown sender is dropped, stop waits for Idle publication only within one bounded backstop, and a probe that outlives the backstop leaves the lifecycle Stopping until its generation is retired.

The disposable Debian or Ubuntu guest gate runs in two phases around a real reboot, with the real production-intent cargo-deb package (host and adapter identity-verified from its extracted payload before staging) installed in phase 1 so every real-gate operation runs through the shipped deb path with the production adapter. Crash, fault, and adversarial cases swap in the sandbox-intent adapter at that same deb path (never a second carrier), and the production adapter is restored for the real dpkg remove/upgrade lifecycle through the shipped prerm/postrm scripts and the post-release state. The gate covers adopt, hold, status, release with the real package manager, kill during adoption at the unnamed-staged-write, staged-link, and publication boundaries (the first leaves no named residue; the second leaves a complete hash-matchable staged file), a real mid-adoption reboot resume, operator drift, upgrade, full-upgrade, unattended-upgrade, collision, unprivileged read-only status, the module-version snapshot, cross-process lock contention between real processes, the raw-artifact activation refusal, injected publish-fsync and release-fsync failures (the first durably unwinds the published fragment; the second persists release evidence and retries cleanly), an exact byte-for-byte staged collision with a new inode (preserved, adoption aborted), a direct journal cycle with both exact journal paths absent at the end, an operator /var/lib neighbor surviving byte for byte, a crash after the journal stage link recovered by the next locked enable, an operator entry at the fixed recovery stage failing closed and preserved, a wrong-inode journal copy at the fixed stage failing closed and preserved, a dangling fragment symlink (drift; release refuses with evidence), a symlink-swapped preferences-parts directory (refused), staged-fault recovery, and final residue checked with lstat semantics (fragment, canonical journal, recovery stage, staged, and preferences leftovers all absent).

The host manual scenario covers a real NVIDIA driver swap. Guests cannot verify real driver state because guest images ship no NVIDIA module; the journal and package machinery are guest-provable, the driver scenario is not.
